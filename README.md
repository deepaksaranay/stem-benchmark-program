# STEM Benchmark Program

A practice project that models how a **STEM AI-evaluation program** is built and run: verified physics and
math tasks, an automatic grader, quality and throughput metrics, and a delivery report.

> **Read this first.** This is a self-built portfolio project. The model answers and the contributor/reviewer
> workflow log are **synthetic** (generated by a script with a fixed seed). No real customer, team or program
> is behind them. See [docs/06-honest-scope.md](docs/06-honest-scope.md) for what this does and does not show.

## The flow

```
customer request
      |
      v
program charter (scope, acceptance criteria, plan, risks)            docs/01, docs/05
      |
      v
task specs (tasks/tasks.json) --- contributors write them            docs/02
      |
      v
TWO independent reference solutions per task (analytic + numeric)    benchmark/reference.py
      |   must agree within a tolerance
      v
answer key (generated, never typed by hand)                          tasks/answer_key.json
      |
      +--> reviewers score tasks with a rubric                       docs/03
      |         |
      |         v
      |    workflow log --> metrics (quality, speed, throughput)     benchmark/metrics.py
      |
      +--> model answers --> safe grader (units, tolerance)          benchmark/verify.py
                                     |
                                     v
                          delivery report (RAG status)               reports/delivery_report.md
```

## Quick start

Works with Python 3.11 or newer (including 3.14). On Windows, call the virtual environment's Python
directly. This needs no activation, so Windows' script policy cannot block it:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m benchmark validate-tasks
```

Prefer `python -m ...` without the long prefix? Activate once with `.venv\Scripts\Activate.ps1`. If PowerShell
blocks it, run `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` first. On Linux/macOS use
`source .venv/bin/activate`.

The commands below are written as `python -m benchmark ...`; use the `.venv\Scripts\python.exe` prefix if you did not
activate.

Commands:

| Command | What it does |
|---|---|
| `python -m benchmark validate-tasks` | Checks specs, runs both solutions of every task, checks the answer key |
| `python -m benchmark build-key` | Regenerates `tasks/answer_key.json` (refuses if two solutions disagree) |
| `python -m benchmark build-key --check` | Fails if the key is out of date (used in CI) |
| `python -m benchmark evaluate data/synthetic_submissions_model_a.json` | Grades one model's answers |
| `python -m benchmark metrics` | Production metrics from the workflow log |
| `python -m benchmark report` | Writes `reports/delivery_report.md` |
| `python -m benchmark demo-data` | Regenerates the synthetic demo data |

## What is in here

| Path | Contents |
|---|---|
| `tasks/tasks.json` | 12 tasks (6 physics, 6 mathematics) with prompts, units, tolerance |
| `benchmark/reference.py` | Two independent solutions per task (SymPy/closed form vs SciPy/NumPy/mpmath) |
| `benchmark/verify.py` | Safe answer parser (no `eval`), unit conversion, grading outcomes |
| `benchmark/evaluate.py` | Grades a model and summarises by domain and difficulty |
| `benchmark/metrics.py` | First-pass rate, rework rate, turnaround median/p90, weekly throughput, RAG |
| `benchmark/report.py` | The delivery report |
| `data/` | Synthetic model answers, synthetic workflow log, program targets |
| `docs/` | Charter, contributor guidelines, reviewer rubric, metrics definitions, risk register, honest scope |
| `tests/` | 81 tests |
| `.github/workflows/ci.yml` | Lint, tests, task validation, key check, report artifact |
| `Dockerfile` | Runs the CLI in a container |

## Design decisions worth explaining

1. **Two solutions per task.** A wrong reference answer is the most costly mistake in a benchmark. If the analytic
   and the numeric method disagree, the task cannot be built (`build-key` refuses).
2. **The answer key is generated.** Nobody types it. CI fails if the key and the solutions drift apart.
3. **Model answers are untrusted input.** The grader never calls `eval`. It parses a small whitelist of syntax and
   rejects things like `__import__('os')` or `9**9**9`. The tests cover these cases.
4. **Units are part of correctness.** `90.35` without a unit, or `90.35 s` for a distance, is a `unit_error`;
   `0.09035 km` is correct.
5. **Averages hide problems.** The report shows the 90th percentile and per-person breakdowns. In the demo data the
   overall figures look acceptable while one reviewer is far slower and one contributor is far below target.
6. **Every RED needs an action.** The report ends with what a program owner would do.

## Tests

```powershell
python -m pytest -q          # 81 tests
python -m flake8             # style
```
Highlights: the safe parser against hostile input, unit and tolerance edge cases, the dual-solution agreement
for every task, a deliberately broken reference being caught, exact metric values on a small hand-made log, and a
check that the committed demo files and report equal what the generator produces.

## Docker

```powershell
docker build -t stem-benchmark .
docker run --rm stem-benchmark validate-tasks
```

## Ideas to extend it

- Add more tasks (aim for 50) and a new topic. Each needs two solutions.
- Add a command that calls a real model API and grades its answers (keep keys out of Git).
- Store the workflow log in SQLite and add a dashboard.
- Add inter-reviewer agreement (for example Cohen's kappa) to the metrics.
- Add a `difficulty calibration` check: tasks that every model solves are too easy.
